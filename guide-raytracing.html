Hardware Ray Tracing M3+ only

MetalTerrain can use Apple Silicon's hardware ray-tracing units for ray-traced sun shadows on terrain. Shadow rays are traced from each surface point toward the sun against an acceleration structure built from the actual chunk geometry — mountains and cliffs cast true shadows on each other.

Supported hardware

See the full matrix on Chip Support. In short: M3/M4/M5 (all variants) and A17 Pro / A18 / A18 Pro / A19 / A19 Pro and later. Not supported: M1/M2 (all variants), A16 and earlier.

The library never assumes support from the device name — it queries device.supportsRayTracing via MTCapabilities.

Enabling it

Two gates, both required:

  1. Build gate — the M3_FEATURES Swift compilation condition. All ray-tracing code compiles only when this flag is set, e.g. 
    // swift build:
swift build -Xswiftc -D -Xswiftc M3_FEATURES

// Xcode: add M3_FEATURES to 'Other Swift Flags'
// AND -DM3_FEATURES to 'Other Metal Compiler Flags'
// (both compilers — without the Metal flag, mesh/RT shaders never compile)
    A standard build (no flag) contains no ray-tracing code at all and runs on every supported device.
  2. Runtime gate — the device check. With the flag on, MTTerrainRenderer calls MTCapabilities.supportsHardwareRayTracing(device:) at init and only creates rayTracing when the GPU answers yes.

You don't do this by hand in the normal case: a renderer built with M3_FEATURES enables ray-traced sun shadows automatically on supported devices, and silently falls back to the analytic shadow path on everything else.

import MetalTerrain

if MTCapabilities.supportsHardwareRayTracing(device: device) {
    // Hardware present. renderer.rayTracing is non-nil only when
    // the library was ALSO built with M3_FEATURES.
}

How acceleration structures work here

  • BLAS (bottom-level): one per chunk. Each visible chunk's triangle mesh is baked into its own bottom-level acceleration structure — built once when the chunk's buffers are created, dropped when recycled.
  • TLAS (top-level): one per frame. Built over the visible chunk set with each chunk's world transform. This is what the shadow pass intersects against.

Rebuild policy: the TLAS rebuilds when the visible chunk set changes (the same streaming in renderer.update(cameraTarget:)). Chunks never move or deform once built — a stable camera means a stable TLAS and zero build cost per frame.

// The renderer calls this for you; public for custom integrations:
rayTracing.update(chunks: [
    (id: 0, vertexBuffer: vb0, indexBuffer: ib0, indexCount: n0, transform: t0),
    // … one entry per visible chunk
])

Performance notes

  • Build cost is the whole price. BLAS once per chunk, TLAS once per visible-set change. Steady state costs one ray per fragment in the shadow pass — what the hardware units are for.
  • Fast camera moves cost builds, not hitches. Streaming bounds new chunks per frame; shadows may lag a frame behind new geometry, never a frame drop.
  • Memory: each BLAS is roughly proportional to the chunk's vertex buffer; released with the chunk.

Caveats: new and needs device testing — shadow quality and build latency on A17 Pro-class GPUs are unvalidated. Ray tracing covers sun shadows on terrain only; structures, water, and skybox use existing paths. On unsupported devices the analytic shadow term is used and the visual difference is intentionally subtle.
