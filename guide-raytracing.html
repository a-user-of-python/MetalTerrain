Hardware Ray Tracing M3+ only

MetalTerrain can use Apple Silicon's hardware ray-tracing units for ray-traced sun shadows on terrain. Shadow rays are traced from each surface point toward the sun against an acceleration structure built from the actual chunk geometry — mountains and cliffs cast true shadows on each other.

Supported hardware

See the full matrix on Chip Support. In short: M3/M4/M5 (all variants) and A17 Pro / A18 / A18 Pro / A19 / A19 Pro and later. Not supported: M1/M2 (all variants), A16 and earlier.

The library never assumes support from the device name — it queries device.supportsRayTracing via MTCapabilities.

Enabling it

Two gates, both required:

  1. Build gate — the M3_FEATURES Swift compilation condition. All ray-tracing code compiles only when this flag is set, e.g. 
    // swift build:
swift build -Xswiftc -D -Xswiftc M3_FEATURES

// Xcode: add M3_FEATURES to 'Other Swift Flags'
// AND -DM3_FEATURES to 'Other Metal Compiler Flags'
// (both compilers — without the Metal flag, mesh/RT shaders never compile)
    A standard build (no flag) contains no ray-tracing code at all and runs on every supported device.
  2. Runtime gate — the device check. With the flag on, MTTerrainRenderer calls MTCapabilities.supportsHardwareRayTracing(device:) at init and only creates rayTracing when the GPU answers yes.

You don't do this by hand in the normal case: a renderer built with M3_FEATURES enables ray-traced sun shadows automatically on supported devices, and silently falls back to the analytic shadow path on everything else.

import MetalTerrain

if MTCapabilities.supportsHardwareRayTracing(device: device) {
    // Hardware present. renderer.rayTracing is non-nil only when
    // the library was ALSO built with M3_FEATURES.
}

How acceleration structures work here

  • BLAS (bottom-level): one per chunk. Each visible chunk's triangle mesh is baked into its own bottom-level acceleration structure — built once when the chunk's buffers are created, dropped when recycled.
  • TLAS (top-level): one per frame. Built over the visible chunk set with each chunk's world transform. This is what the shadow pass intersects against.

Rebuild policy: the TLAS rebuilds when the visible chunk set changes (the same streaming in renderer.update(cameraTarget:)). Chunks never move or deform once built — a stable camera means a stable TLAS and zero build cost per frame.

// The renderer calls this for you; public for custom integrations:
rayTracing.update(chunks: [
    (id: 0, vertexBuffer: vb0, indexBuffer: ib0, indexCount: n0, transform: t0),
    // … one entry per visible chunk
])

Performance notes

  • Build cost is the whole price. BLAS once per chunk, TLAS once per visible-set change. Steady state costs one ray per fragment in the shadow pass — what the hardware units are for.
  • Fast camera moves cost builds, not hitches. Streaming bounds new chunks per frame; shadows may lag a frame behind new geometry, never a frame drop.
  • Memory: each BLAS is roughly proportional to the chunk's vertex buffer; released with the chunk.

Caveats: new and needs device testing — shadow quality and build latency on A17 Pro-class GPUs are unvalidated. Ray tracing covers sun shadows on terrain only; structures, water, and skybox use existing paths. On unsupported devices the analytic shadow term is used and the visual difference is intentionally subtle.

How it works, concretely

When the build flag M3_FEATURES is set and the device has hardware ray-tracing units, the renderer builds two levels of acceleration structure:

  • BLAS (bottom-level): one per terrain chunk, built from the chunk's triangle soup. Cached by chunk ID; evicted when the chunk leaves the visible set.
  • TLAS (top-level): one for the whole scene, instancing every visible chunk's BLAS with identity transforms (chunk meshes are already in world space).

The shadow pass binds the TLAS at fragment buffer index 3 and switches to the terrain_fragment_rt pipeline variant. Rays are traced from the surface point toward the sun; anything the ray hits is in shadow.

chunks stream in ─▶ BLAS per chunk (cached by id)
                        │
visible set changes ────┴─▶ TLAS rebuild (throttled: every 15 frames)
                                │
                    terrain_fragment_rt traces sun rays against TLAS
                                │
                    hit → shadowed │ miss → lit (× analytic shading)

Design intent: subtle, not dramatic

The ray-traced shadows enhance the analytic shadows rather than replacing them. On real terrain the effect reads as "contact shadows are a bit deeper and more correct in the valleys" — not as a different lighting model. If you're expecting dramatic long sunset shadows, adjust sunElevation low; the RT shadows follow the same sun as everything else.

Enabling it

Two conditions, both required:

  1. Compile with the M3_FEATURES Swift and Metal build flag.
  2. Run on M3/M4/M5 (any variant), A17 Pro, A18/A18 Pro, or A19/A19 Pro+.

The renderer checks MTCapabilities.supportsHardwareRayTracing(device:) in init and keeps the MTRayTracing instance only when both hold. There is no public on/off switch and no software fallback — on unsupported configurations the standard analytic shadow path renders, pixel-identical to a non-M3 build.

// Check at startup (e.g. to show/hide an "Enhanced" toggle):
let rtOK = MTCapabilities.supportsHardwareRayTracing(device: device)

// At runtime (M3_FEATURES builds only):
if terrainView.rayTracingActive {
    // The TLAS exists and the RT shadow pipeline is engaged this frame.
}

Performance characteristics

  • BLAS builds happen as chunks stream in — amortized, off the critical path.
  • TLAS rebuilds are the expensive part. The renderer throttles MTRayTracing.update(chunks:) to every 15 frames, and update itself skips the rebuild when the chunk-id set and transforms are unchanged (one signature comparison). Net effect: no per-frame cost once streaming settles.
  • Per-pixel cost: one shadow ray per fragment in the RT pipeline variant. Bounded and predictable — no recursion, no multi-bounce.
  • If you see hitches correlated with fast movement on M3 builds, the TLAS is the first suspect; the 15-frame throttle exists specifically for this.

API surface

public final class MTRayTracing {
    public init(device: MTLDevice)   // unsupported device → safe no-ops
    public var isSupported: Bool     // HW units AND M3_FEATURES build
    public var topLevelStructure: MTLAccelerationStructure?  // bind at frag buf 3
    public func update(chunks: [(id: Int, vertexBuffer: MTLBuffer,
                                 indexBuffer: MTLBuffer, indexCount: Int,
                                 transform: matrix_float4x4)])
}
// Renderer side:
renderer.rayTracing  // MTRayTracing? — nil without M3_FEATURES or HW support

Limits and non-goals

  • Sun shadows only. No reflections, no ambient occlusion, no global illumination — those would need a very different (and much more expensive) ray budget.
  • Structures and water are not in the acceleration structures; only terrain chunks are traced.
  • The TLAS reflects the visible chunk set, throttled — during very fast flight a newly streamed chunk may shade analytically for a few frames before its BLAS lands. This is intentional (smoothness over exactness).
