Mesh Shading M3+ only

On M3-family GPUs, MetalTerrain can replace the standard vertex pipeline with mesh shaders: instead of the CPU expanding every chunk vertex, the GPU generates vertices itself from the chunk's heightmap.

What changes

Standard pathMesh-shader path
Vertex expansionCPU MTMeshBuilder builds a full indexed vertex buffer per chunkGPU mesh shader expands the heightmap on-chip
LOD / cullingCPU decides per chunkObject shader decides per chunk per frame, culls off-screen chunks to zero workgroups
UploadFull vertex buffer per chunkCompact heightmap only

Supported hardware

Same list as ray tracing: M3/M4/M5 (all variants), A17 Pro / A18 / A18 Pro / A19 / A19 Pro+. Not: M1/M2 (all variants), A16 and earlier. Runtime check: device.supportsFamily(.apple9) via MTCapabilities.supportsMeshShading(device:). Full matrix: Chip Support.

Enabling it

Same two gates as ray tracing:

  1. Build gate: compile with the M3_FEATURES Swift compilation condition (plus -DM3_FEATURES for the Metal compiler).
  2. Runtime gate: MTCapabilities.supportsMeshShading(device:) must return true.

A renderer built with M3_FEATURES switches to the mesh-shader path automatically on supported GPUs and falls back to CPU mesh generation otherwise. No separate API — chunk streaming, update, and draw behave the same from the outside.

What the shaders decide

Object shader — per chunk, per frame

Receives the chunk's bounds and heightmap reference; outputs workgroup count and LOD:

  • LOD selection: distance from camera picks grid density, mirroring the standard path's LOD table.
  • Culling: chunks fully outside the frustum (or below the terrain horizon) emit zero workgroups.

Mesh shader — per workgroup

Reads height samples from the chunk heightmap, computes world-space positions, normals, and biome colors exactly as MTMeshBuilder does on the CPU, and emits the triangle grid.

Visual parity

The mesh-shader path is a performance optimization, not a visual upgrade. Same heights, same normals, same biome colors, same LOD table, same lighting. If you ever see a difference between the two paths at the same seed and camera, that's a bug.

When it matters

The mesh path pays off most at high chunkResolution and high viewDistance — where CPU vertex expansion and buffer uploads dominate. See Performance.

See also

  • Ray Tracing — mesh-shaded chunks still provide BLAS geometry for shadows.

The two paths, side by side

StageStandard path (all devices)Mesh-shader path (M3+/A17 Pro+)
Height samplingCPU: MTMeshBuilder on background queue GPU: mesh shader samples the heightmap texture
Vertex emissionCPU writes MTLBuffers Mesh shader emits triangles directly
Frustum cullingCPU: per-chunk AABB test Object shader: culled chunks dispatch zero threadgroups
LOD selectionCPU: buildLOD stride Object shader: threadgroup count from chunk LOD
Fragment shadingPixel-identical (mesh_terrain_fragment ≡ terrain_fragment)

Shader anatomy

  • Object shader (mesh_terrain_object): one threadgroup per chunk. Performs frustum culling and computes how many mesh threadgroups to dispatch based on the chunk's LOD. This is where off-screen chunks die for free.
  • Mesh shader (mesh_terrain_mesh): one threadgroup per 8×8-quad tile. Samples the heightmap, computes positions, normals, and biome colors, applies procedural detail displacement, and emits triangles — no CPU vertex buffers involved.
  • Fragment shader (mesh_terrain_fragment): identical to the standard fragment shader, including the smooth wireframe overlay and per-material lighting.

Engagement and fallback

// M3_FEATURES builds only. Default true; engages only when ALL hold:
//   1. M3_FEATURES compiled in
//   2. GPU is Apple family 9+ (M3/M4/M5, A17 Pro+)
//   3. The mesh pipeline compiled successfully (best-effort async)
terrainView.meshShadingEnabled = true   // set false to force the standard path

// Query support (pure query, safe at startup):
MTCapabilities.supportsMeshShading(device: device)

Fallback is automatic and silent: if mesh shading is unavailable or the pipeline fails to compile, the renderer uses the standard vertex-shader path. The visual result is identical — mesh shading is a performance optimization, not a visual feature. The mesh pipeline compiles asynchronously (Task + await); the standard path renders until it lands, so there's no startup hitch.

What it buys you

  • Zero CPU mesh-generation overhead — no MTMeshBuilder on the background queue, no 48-byte-vertex uploads per chunk.
  • GPU-side frustum culling in the object shader — culled chunks cost one threadgroup that immediately exits.
  • Detail displacement for free — the procedural 3D detail (detailAmount) happens naturally as the mesh shader emits vertices.

What it doesn't do

  • It doesn't change what you see. If you're A/B testing and can't tell which path is active, that's correct behavior.
  • It doesn't remove the need for chunk streaming — the object shader still works on the streamed chunk set; it just meshes them on the GPU.
