FAQ & Troubleshooting

The questions that come up in every integration, and the fixes that actually work.

Setup

Black screen, but the app runs and FPS is nonzero

  • Is world assigned to the view/renderer? Nil world renders nothing.
  • Is setCamera called every frame? Breakpoint your onFrame.
  • Is the camera under the terrain? Print eye Y vs. world.worldY(forHeight: world.heightAt(x:z:)).
  • Metal API Validation (scheme settings) will surface pipeline/encoder errors in the console.

"No such module 'MetalTerrain'"

The package isn't linked to your app target. Xcode: app target → General → Frameworks, Libraries, and Embedded Content → add MetalTerrain. For SwiftPM apps, check the dependencies array in Package.swift.

It works on device but crawls in the simulator

Normal. The simulator has no GPU; Metal runs on the CPU. Judge performance only on physical devices.

World shape

My spawn point is in the ocean

Use world.findSafeSpawn() — it spiral-searches for land above sea level and below the peaks. Don't hand-pick coordinates; every seed is different.

There are no mountains / too many mountains

Mountains come from the masked ridged layer (~35% of land), not from noise.ridged alone. For dramatic ranges: noise.ridged = true + higher octaves. For farmland: leave ridged off and lower gain. Always check 3–4 seeds — one seed is never representative.

Rivers don't reach the ocean

Rivers carve toward sea level and are masked to land. If a river dies inland, the local terrain rose above the carve depth — usually a seed with weak continent relief. Try baseFrequency slightly lower (broader landmasses) or a new seed.

The terrain looks "banded" on mountainsides

Biome height bands showing through on steep slopes. The shader already forces rock above ~0.65 height and blends to snow above 0.80; if you customized biomes, make sure your mountain band is wide enough and slopeColor is set.

Rendering

Seams / cracks between chunks

Should not happen in current versions: skirts cover geometric gaps, border normals use true neighbor heights (no lighting seams), and a +1 safety ring prevents eviction holes. If you see a crack: note the seed, camera position, and viewDistance — it's a bug, and those three reproduce it.

Shoreline "swimming" when I move

The water plane is grid-snapped to prevent exactly this. If the waterline crawls, you're likely moving the water level per frame (don't — it's derived from seaLevel) or your camera far plane is fighting depth precision.

Structures look inside-out

Fixed in current versions: structures render double-sided (.none cull mode) because generated low-poly triangles occasionally have inconsistent winding.

Shadows look wrong / missing on M3

Ray-traced shadows need both the M3_FEATURES build flag and M3+/A17 Pro+ hardware. Check terrainView.rayTracingActive at runtime — if false, you're on the analytic path (which is correct and complete on its own).

FPS drops when I drag a slider

You're doing expensive work per tick. Sliders should update uniforms/values every frame but defer rebuilds: debounce buttons (1.5 s), coalesce config changes, and never set world.config per frame — each set bumps configVersion and invalidates all caches.

Performance

How do I hit 60 fps on older devices?

In order: lower viewDistance (quadratic win), lower chunkResolution, set detailAmount = 0, then consider octaves = 3 + warpStrength = 0 in the noise config. See the Performance guide's per-device table.

Memory warnings with large viewDistance

Full-res chunks are ~4.6 MB GPU-side each. At viewDistance 10 that's 441 chunks before culling. The LRU cap bounds it, but if you're still pressured, viewDistance 8 is the practical max on 4 GB devices.

Occasional hitch while flying fast

Chunk streaming saturating the build queue, or a TLAS refresh on M3 builds (throttled to every 15 frames). If it reproduces reliably, capture which: hitches that correlate with movement are streaming; hitches at rest are something else (profile with the Metal debugger).

API confusion

MTTerrainView vs MTTerrainRenderer — which one?

MTTerrainView for 95% of apps: drop it in, assign a world, drive the camera. MTTerrainRenderer when you need your own MTKView, offscreen rendering, or the overlay closure for custom draws (cars, markers, gizmos) in the same render pass.

Where do I put game objects (player, car, enemies)?

In the overlay closure of renderer.draw(in:overlay:) — same encoder, same pass, no sync bugs. MTTerrainView doesn't expose the overlay; use the raw renderer for that.

How do I save/load the world?

Save the seed (and the config, if customized). That's the entire world — regeneration is deterministic. There is no serialization format because there's nothing to serialize.

Can two players share a world?

Yes — send the seed + config once. Both devices generate bit-identical terrain locally. Only gameplay state (positions, inventory) needs networking.

Do I need to handle memory warnings?

The renderer's LRU cache already bounds GPU memory. On didReceiveMemoryWarning you can drop viewDistance a notch; streaming refills as needed.

Still stuck?

  • Reproduce with a seed + config + camera position — determinism means your bug report is a complete repro.
  • Capture a frame with Xcode's Metal debugger for rendering issues.
  • File issues at github.com/a-user-of-python/MetalTerrain.
